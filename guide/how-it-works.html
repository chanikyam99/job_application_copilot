How It Works

The full picture — from browser click to AI output — before you write a single line of code.

This page is your mental model. Read it once before you start building, and refer back to it whenever you feel lost in the details. By the time you finish reading, you should be able to trace any user action all the way through the stack and back.

1 System Architecture

The project runs as two completely separate servers on your local machine. One serves the HTML/CSS/JS files your browser loads. The other runs the Python API that handles data, auth, and AI calls. They communicate over HTTP — the same way a real production app would communicate across the internet.

WHY two servers instead of one?

FastAPI serves JSON data, not HTML pages. Separating static files from the API is standard architecture — it mirrors exactly what you'd do in production (Vercel for frontend, Railway/Render for backend). It also makes the project easier to reason about: everything in frontend/ is just files, everything in backend/ is logic.

2 The 4 Core Flows

Every user interaction in this app reduces to one of four flows. Master these and you understand the entire system.

Flow 1 — Sign Up / Login

How a user gets from the landing page to a valid session, and how that session persists across page loads.

1
User fills in email + password on index.html
The form calls the login or signup handler in index.js.
2
JS calls api.post('/auth/login', { email, password })
The request() function in api.js adds no auth header here — the user isn't logged in yet.
3
FastAPI receives POST /auth/login → auth_router.py
Route is public (no Depends(get_current_user)). Queries the users table for the submitted email.
4
Password is verified with bcrypt: verify_password(plain, hashed)
The stored password is never the raw string — it was hashed at signup time. bcrypt compares the hash.
5
If valid: create_access_token({"sub": email}) → signed JWT string
The payload encodes the user's email and an expiry timestamp. Signed with the app's secret key.
6
Returns { access_token: "eyJ...", token_type: "bearer" }
This is the standard OAuth2 response shape FastAPI uses.
7
JS stores it: auth.setToken(data.access_token) → localStorage
Survives page refresh, browser close and reopen. Cleared on logout or 401 response.
8
JS immediately calls api.get('/auth/me') — now with the Bearer header
Gets back the user object (id, email, full_name). Stored via auth.setUser(user).
✓
Redirects to dashboard.html
From here, every subsequent request() call automatically reads the token from localStorage and adds Authorization: Bearer <token>.

Flow 2 — Create Application (Upload PDF + Fill Form)

How a resume PDF and job description travel from the user's file system into the database — and how the raw bytes become searchable text.

1
User is on Step 1 of new-application.html — selects or drops a PDF file
The file is held in memory by the browser. Nothing is uploaded yet.
2
User fills Step 2 — job title, company name, job description text
A multi-step wizard UI in new-application.js manages which panel is visible.
3
User clicks "Generate My Kit" — JS builds a FormData object
resume_file: the PDF binary  ·  job_title, company, jd_text: text fields. Multipart encoding bundles binary and text in one request.
4
api.postForm('/applications/', formData) → fetch with Content-Type: multipart/form-data
Note: postForm does NOT set the Content-Type header manually — the browser sets it with the correct boundary string automatically when given a FormData object.
5
FastAPI POST /applications/ reads the PDF bytes → extract_text_from_pdf(bytes)
Uses pypdf to extract all pages as plain text. The raw PDF binary is never stored — only the extracted text.
6
Creates an Application row in DB with the extracted text as original_resume
Also stores jd_text, job_title, company, and user_id. Status defaults to not_yet.
7
Returns the new application with its id
The application exists in the DB but no AI output yet. The draft is still empty.
8
JS immediately calls api.post('/applications/{id}/generate')
This kicks off the AI pipeline. The call is async — JS awaits the response while showing a loading screen.
9
Step 3 loading screen appears while waiting (~15 seconds)
An animated progress bar and rotating status messages keep the user informed.
✓
On completion → redirects to application.html?id={id}
The full AI kit is now stored in the DB and ready to display.

Flow 3 — The AI Generation Pipeline Core Feature

This is the heart of the app. One API call triggers four LLM agents — the first runs sequentially, the other three run simultaneously. Here's exactly what happens inside orchestrator.py.

1
Backend receives POST /applications/{id}/generate
Protected route — requires a valid JWT. Fetches the full application row from the DB.
2
Fetches original_resume text and jd_text from the DB row
These two strings are the only inputs the entire AI pipeline needs.
3
Calls run_pipeline(resume_text, jd_text) in orchestrator.py
This is an async function. FastAPI awaits it without blocking other requests.
4
Agent 1 — Fit Analyst (runs first, sequential)
Prompt: "You are a recruiter. Score this resume against this JD." Sent to Groq with temperature: 0.2 (low = consistent, reproducible scoring). Returns structured JSON:
{ match_score: 78, matching_requirements: [...], missing_requirements: [...], keywords: [...] }
Takes ~3–5 seconds. Its output is passed directly to Agents 2, 3, and 4.
5
Agents 2, 3, 4 launch simultaneously via asyncio.gather()
All three get the resume, JD, and Agent 1's analysis as context. They run as concurrent coroutines:
Agent 2 · Resume Writer
Rewrites resume to match JD keywords.
Returns: { rewritten_resume, changes: [{original, rewritten, reason}] }
Agent 3 · Cover Letter
Writes a 1-page cover letter, tone-matched to the company.
Returns: plain text (not JSON).
Agent 4 · Interviewer
Generates 10 Q&As.
Returns: [{type, question, sample_answer, tip}]
6
All results saved to the drafts table as JSON strings
Each agent output is serialized with json.dumps() before storage. This avoids 4 extra relational tables.
✓
Returns ApplicationOut with the complete draft object embedded
Total wall-clock time: ~15 seconds. Sequential would be ~45 seconds — a 3× speedup from parallelism.

WHY run Agent 1 first?

Agents 2, 3, and 4 all benefit from knowing the fit score and missing keywords before they write. Agent 2 uses the keyword list to know exactly what to weave into the resume. Agent 3 uses the missing requirements to address them proactively in the cover letter. Agent 4 uses them to generate questions the interviewer will likely ask. Agent 1's output makes the other three outputs measurably better.

Flow 4 — Viewing Results

How the stored JSON strings become the interactive tabs, animated score rings, and downloadable files the user sees on application.html.

1
application.html loads, reads ?id=123 from the URL
new URLSearchParams(window.location.search).get('id') — no page router needed.
2
Calls api.get('/applications/123') → returns full ApplicationOut with embedded draft
One HTTP call fetches everything. The draft is nested inside the application JSON response.
3
Draft fields are JSON strings — JS parses them: JSON.parse(app.draft.fit_analysis)
The database stores agent output as text. JS deserializes each field back into a live object when rendering.
4
Fit Analysis tab: reads match_score → animates SVG ring via stroke-dashoffset
Renders matching/missing requirement lists and keyword tags. The ring animation runs on requestAnimationFrame.
5
Resume tab: original text left panel, rewritten text right panel; change cards below
Each change card in the changes array shows what was rewritten and why.
6
Cover Letter tab: displays draft.cover_letter as <pre> text; Download button triggers .docx generation
GET /applications/123/download/cover-letter → backend uses python-docx to generate bytes → browser receives the file with a Content-Disposition: attachment header.
7
Interview Prep tab: renders accordion cards, one per Q&A in the interview_qa array
Each card has a type badge (behavioral / technical / situational), the question, a sample answer, and a coaching tip. Click to expand.

3 Authentication Flow (JWT Lifecycle)

JWT (JSON Web Token) is how the app knows who you are on every request — without storing any session data on the server. Here is the full lifecycle:

LOGIN
Server creates token: jwt.encode({"sub": email, "exp": now + 7 days}, SECRET_KEY)
The token is just a signed string — it encodes claims and an expiry. If you decode it at jwt.io you can read the payload (but can't forge it without the secret key).
STORED
localStorage.setItem('token', access_token)
Persists across browser tabs and page refreshes. Cleared by auth.logout() or automatically on 401.
EVERY REQ
The request() function in api.js adds Authorization: Bearer eyJhbGci...
This happens automatically for every fetch — you never write the header manually in your page JS.
SERVER
get_current_user() FastAPI dependency decodes the token, extracts email, queries DB
This dependency is injected into every protected route. The route handler receives the user object — it never touches token logic itself.
✓ VALID
Endpoint gets current_user object injected — processes the request normally.
The user's id from this object is used to scope all DB queries — you can only see your own applications.
✗ INVALID
401 returned → request() auto-clears localStorage + redirects to login
Happens if the token is expired (7 days), tampered with, or if someone manually forged a token with the wrong key.
WHY stateless auth?

The server never stores sessions. No session table. No Redis. The token is the proof of identity — as long as it is signed with the correct secret key and not expired, the server can verify it with pure computation. This means the backend can be restarted, scaled to multiple instances, or moved to a serverless function — and existing logged-in users are unaffected.

Key design decisions

Decision How it works Why
1-to-1 draft relationship relationship("Draft", uselist=False) on the Application model — SQLAlchemy returns a single object instead of a list Each application generates exactly one kit. Enforced at the ORM level, not just by convention.
Cascade deletes cascade="all, delete-orphan" on the relationship Delete a user → their applications are deleted → their drafts are deleted. No orphan rows ever build up.
Agent outputs as JSON text json.dumps(result) before INSERT, json.loads() after SELECT Avoids 4 extra tables (fit_requirements, resume_changes, interview_questions…). The structure is defined by the agent prompt, not the DB schema.
Status as Python Enum class ApplicationStatus(str, Enum): not_yet / applied / interviewed / rejected / offer SQLite has no native enum type — storing as text is fine. Python Enum gives type safety and IDE autocompletion. FastAPI validates it automatically in request bodies.

5 The Two-Server Setup

You will run two terminal processes every time you develop. Here is why each one exists and what it does.

🖥️ Backend — port 8000
uvicorn main:app --reload --port 8000

FastAPI handles all API logic, database reads/writes, PDF parsing, JWT verification, and Groq API calls. Must be running for any data operation to work.

🌐 Frontend — port 3000
python -m http.server 3000

Serves static HTML/CSS/JS files. No logic at all — just bytes on request. In production you would replace this with Nginx, Vercel, or Netlify. Can be any static file server.

Why CORS is required

When JavaScript running on localhost:3000 tries to make a fetch request to localhost:8000, the browser treats these as different origins (different ports = different origins). By default, the browser blocks such cross-origin requests to prevent malicious sites from silently reading your bank's API.

The CORSMiddleware in main.py — configured with allow_origins=["*"] — sends back HTTP headers that tell the browser: "Yes, this API explicitly allows requests from any origin." The browser then allows the fetch to proceed.

⚠ Note

allow_origins=["*"] is fine for local development and learning. In a real production deployment, lock this down to your actual frontend domain — e.g., allow_origins=["https://myapp.vercel.app"] — to prevent other websites from using your API on behalf of your users.

The two commands to start the project

bash  Terminal 1 — backend/ (venv activated)
uvicorn main:app --reload --port 8000
bash  Terminal 2 — frontend/
python -m http.server 3000
WHY not just use FastAPI to serve the HTML too?

You could — FastAPI supports StaticFiles mounting. But keeping them separate is better practice for learning: it makes the API/frontend boundary explicit, forces you to think about CORS and auth headers, and matches the real-world pattern you will follow on every professional project. The discipline of treating the frontend as a completely separate client pays off.
