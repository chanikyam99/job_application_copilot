Section 08

Frontend HTML Pages

Four pages form the complete UI: a login/signup screen, a dashboard, a creation wizard, and a results viewer. Each page is a self-contained module — no build step, no framework.

Bug fixes applied — API URLs corrected

The original guide contained several incorrect API URLs in the JavaScript examples. The source files have been corrected and the code shown below reflects the fixed versions. Specifically: the status PATCH now targets /applications/${appId}/status; the cover letter download uses /applications/${appId}/download/cover-letter; regenerate calls use the path parameter form /applications/${appId}/regenerate/${section}; and the section name values passed to regenerate are fit_analysis, resume, cover_letter, interview. See Section 10 for a full list of bugs fixed.

Page Map

The frontend is four plain HTML files. Each loads js/config.js as a plain script in <head> before importing js/api.js as an ES module. Navigation between pages is just window.location.href.

FileRoutePurpose
index.html/Login & signup — gateway to the app
dashboard.html/dashboard.htmlApplication list with stats, filters, and cards
new-application.html/new-application.html3-step wizard: upload resume → job details → generating

WHY plain HTML files instead of a framework

The app has 4 distinct pages, each with completely different layout concerns. A framework like React would need routing, a build pipeline, and component boilerplate. Vanilla HTML gives us instant reloads, zero config, no node_modules, and pages that are trivially hostable from any static file server — including Python's built-in one. The only shared state is the JWT in localStorage.

1 frontend/index.html — Login & Signup

The entry point. A split-screen layout divides the viewport: the left panel is a hero/branding column that never scrolls; the right panel contains the auth form. A tab switcher toggles between Sign In and Create Account without any page reload.

What happens on load

The very first line of the <script type="module"> block calls auth.isLoggedIn(). If a valid token already exists in localStorage, the page immediately redirects to dashboard.html — the user never sees the form. This prevents the awkward back-button loop after login.

Auth flow

  1. User submits the login form → POST /auth/login returns { access_token }
  2. Token is saved: auth.setToken(data.access_token)
  3. A second call to GET /auth/me fetches the user object and saves it: auth.setUser(user)
  4. Redirect to dashboard.html

Signup does the same two-step: create account, then immediately log in automatically so the user lands on the dashboard without an extra sign-in screen.

WHY fetch /auth/me after login instead of decoding the JWT

The JWT payload could theoretically be decoded client-side (it is base64), but that couples the frontend to the JWT structure. Calling /auth/me is one extra request, but it gives us a clean, typed user object (including full_name) and works even if the JWT format changes. The extra round-trip is invisible at login time.

WHY type="module" on the script tag

ES module imports (import { api, auth } from './js/api.js') only work inside <script type="module">. As a bonus, module scripts are deferred automatically — they run after the DOM is parsed, eliminating the need for DOMContentLoaded listeners. All four pages use this pattern.

2 frontend/dashboard.html — Applications List

The main hub. After login, every session starts here. It shows a stats summary row, a status filter bar, and a responsive card grid of all job applications. A card click navigates to application.html?id=X for the full detail view.

Data flow

  1. requireAuth() runs first — if no token, redirect to index.html immediately
  2. loadApps() calls GET /applications/ and stores the response in allApps
  3. Stats counters are derived by filtering allApps in-memory (no extra API calls)
  4. renderApps() applies the active filter and rebuilds the grid via innerHTML

Filter system

Filter buttons each carry a data-filter attribute matching the backend status enum values (not_yet, applied, interviewed, rejected, offer). Clicking any button sets activeFilter and calls renderApps() — no network request needed since all data is already in memory.

WHY store all apps in memory and filter client-side

A typical user has fewer than 100 applications. Fetching once and filtering in-memory means every filter click is instantaneous. Server-side filtering via query params would add a round-trip (50–200ms) for each click with no benefit at this data scale. If the app ever scaled to thousands of records, you would add a debounced search and server-side pagination — but that is not this problem.

WHY innerHTML for the card grid instead of createElement

Template literal HTML strings are readable, reviewable, and easy to edit. document.createElement for a card with 8 nested elements would be 40 lines of imperative code for every card. The security concern (XSS) is not relevant here because all data comes from our own authenticated API — we are not rendering user-supplied raw HTML from untrusted sources.

3 frontend/new-application.html — Create Application

A 3-step linear wizard. The steps are shown/hidden by toggling CSS classes — they are all in the DOM simultaneously. This avoids any state serialization between screens.

Step 1: Resume Upload

A drag-and-drop drop zone listens for dragover, dragleave, and drop events. Dropping a file or clicking to browse stores the file in a module-level variable. The zone shows the selected filename and enables the Next button.

Step 2: Job Details

A form collects job title, company name, and the full job description text. On submit, a FormData object is built containing both the file and the text fields, then sent as a multipart POST /applications/ request. The API returns the new application ID immediately (before AI generation starts).

Step 3: Generating

Once the application record is created, a second call to POST /applications/{id}/generate kicks off the AI pipeline. The UI shows an animated progress display with step labels while the backend runs. When the response resolves (~15–30 s), the page redirects to application.html?id={id}.

WHY two separate API calls (create then generate)

Bundling file upload and AI generation into one request would mean a single HTTP connection held open for 30 seconds. Some proxies and browsers will time out. Splitting into two calls lets us: (1) confirm the upload succeeded instantly, (2) show a meaningful progress UI for the generation phase, and (3) recover gracefully if generation fails — the application record already exists and can be retried.

WHY FormData for the upload instead of JSON

The PDF file is binary data. JSON can only carry text (base64 encoding adds ~33% size overhead and a conversion step). FormData sends the file as a binary stream alongside the text fields in a single multipart request — the natural format for file uploads. FastAPI's File() and Form() parameters receive it directly.

4 frontend/application.html — View Results

The results page displays all four AI-generated artifacts in a tabbed layout. The page loads the full application record via GET /applications/{id}, then parses each artifact from the draft JSON field and populates the appropriate tab panel.

Tab 1: Fit Analysis

An SVG score ring (circumference 276.46 px — the exact value for a circle with r=44) renders the numeric match score as a colored arc. Below it, matching requirements are shown as green tags and missing ones as red tags. The score integer drives the ring's stroke-dashoffset.

Tab 2: Resume

A two-column diff view shows the original bullet points alongside the rewritten versions. Changed lines appear with the original struck through in red and the replacement in green. The agent returns a structured list of changes that drives this rendering.

Tab 3: Cover Letter

Plain text displayed in a readable container. A "Download .docx" button calls GET /applications/{id}/download/cover-letter which streams a binary response — the frontend uses api.getBlob(), creates a temporary object URL, and triggers a download link click programmatically. A "Regenerate" button calls POST /applications/{id}/regenerate/cover_letter (path parameter, not query string).

Tab 4: Interview Prep

Ten accordion cards, one per question. Each card shows the question type badge (behavioral, technical, situational), a sample answer, and a coaching tip. Clicking a card header toggles the answer panel open/closed via a CSS class.

WHY store all artifacts in a single JSON field (draft)

The four artifacts are always generated and consumed together. A single draft JSON column is simpler than four separate columns or a separate artifacts table. The structure can evolve (add fields, rename keys) without a database migration. Retrieval is one query, and the entire kit can be re-stored atomically when regenerated.

WHY SVG for the score ring instead of a CSS border-radius trick

CSS circular progress requires layered pseudo-elements with clip-path or conic-gradient — the latter has limited browser support for animated transitions. An SVG <circle> with stroke-dasharray and stroke-dashoffset is the standard approach: it works in every modern browser, is easily animated with CSS transitions, and the math is clean (offset = circumference × (1 − score/100)).
