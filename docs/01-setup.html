Section 01

Architecture & Setup

Every tool decision explained. Read this before writing any code — understanding WHY each piece exists makes the rest obvious.

Tool Decisions

LayerChoiceWHY (one sentence)
FrontendVanilla HTML + CSS + JS4-page CRUD app with tabs and diff views — Streamlit's rerun model can't handle this cleanly
BackendFastAPI + UvicornAsync-native (critical for 15-second AI calls), Pydantic validation built-in, auto Swagger docs
DatabaseSQLite + SQLAlchemyZero-setup file-on-disk for dev; swap DATABASE_URL to Postgres for deploy without changing any code
LLMGroq llama-3.3-70bFree tier, 5–10x faster than OpenAI, API-compatible so switching later is 3 lines
Multi-agentHand-rolled coordinatorSequential → parallel DAG is 10 lines of asyncio.gather(); LangGraph would add 200 lines of boilerplate for zero benefit
PDF parsepypdfPure Python, no system deps (no Poppler), handles text-based PDFs well
AuthJWT in localStorageStateless, works across page navigations, taught in M3 — simpler than cookie + session setup
Downloadpython-docxDe facto standard for .docx generation; users can edit the cover letter after download
WHY asyncio.gather() is the key architectural win

Agent 1 (fit analysis) must run first — its output feeds the other 3 agents. But Agents 2, 3, and 4 are independent of each other. Running sequentially: ~45 seconds (3 × 15s). Running with asyncio.gather(): ~15 seconds (the slowest of the three). FastAPI is async-native, so this works without threading.

2 Create the Virtual Environment

WHY a virtual environment?

Isolates your project's packages from the system Python. Without it, installing groq==0.9.0 could silently break another project that uses a different version. Always use venv for Python projects.

terminal — from inside backend/ bash 
# Create the virtual environment
python -m venv venv

# Activate it:
# Windows:
venv\Scripts\activate

# Mac / Linux:
source venv/bin/activate

# Your prompt should now show (venv) at the start

4 Procfile

Create backend/Procfile (no file extension). This file tells Render and Railway exactly how to start the web process:

backend/Procfile txt 
web: uvicorn main:app --host 0.0.0.0 --port $PORT
WHY $PORT and not a hardcoded number?

Cloud platforms (Render, Railway, Heroku) allocate ports dynamically at runtime — they set the $PORT environment variable and then route external traffic to it. If you hardcode --port 8000, the platform's router can't reach your process and the deploy fails with a "service did not bind to the expected port" error. The --host 0.0.0.0 flag tells uvicorn to accept connections on all network interfaces, not just localhost.

backend/.env.example env

ALGORITHM=HS256

# ── AI ────────────────────────────────────────────────────────────────────────

# ── Database ──────────────────────────────────────────────────────────────────
# Local dev (SQLite):
DATABASE_URL=sqlite:///./job_copilot.db

# Production (PostgreSQL — Render / Railway add PostgreSQL and give you this URL):
# DATABASE_URL=postgresql://user:password@host:5432/dbname

# ── CORS ─────────────────────────────────────────────────────────────────────
# Comma-separated list of allowed frontend origins.
# Leave as * for local dev. Set to your deployed frontend URL in production.
# Example: ALLOWED_ORIGINS=https://your-app.onrender.com
ALLOWED_ORIGINS=*
WHY commit .env.example but not .env?

.env.example is safe to commit because it contains no real secrets — it's pure documentation showing what variables the app expects. The real .env file (with your actual API key and secret key) must be added to .gitignore and never committed. On Render/Railway, you set these variables directly in the platform's "Environment" dashboard instead of uploading a .env file.

6 frontend/js/config.js

Create frontend/js/config.js. This is a plain script (not an ES module) that sets window.BACKEND_URL based on which hostname the page is loaded from:

frontend/js/config.js javascript 
// ─── Backend URL Configuration ───────────────────────────────────────────────
// Auto-switches between local dev and the deployed cloud backend.
// After deploying to Render / Railway, replace the URL below with your
// actual backend service URL (e.g. https://job-copilot-api.onrender.com).
// ─────────────────────────────────────────────────────────────────────────────
window.BACKEND_URL = (
  location.hostname === 'localhost' ||
  location.hostname === '127.0.0.1'  ||
  location.hostname === ''
)
  ? 'http://localhost:8000'
  : 'https://YOUR_BACKEND.onrender.com'; // <-- replace after deploying
WHY a separate config.js and WHY must it load first?

The API module (frontend/js/api.js) reads window.BACKEND_URL at the top of its file when it is first imported. If config.js hasn't run yet, window.BACKEND_URL is undefined and every API call silently fails or hits the wrong URL.

The fix is load order: config.js must appear as a plain <script> tag before any <script type="module"> tags in every HTML page's <head>. Plain scripts run synchronously and block parsing; ES modules are deferred, so the plain script always finishes first.

The hostname check means the same source file works for both local development (localhost:8000) and the deployed cloud backend — you only need to update the Render URL once after your first deploy.

Load order in every HTML page

Every HTML page must include these two tags in this exact order inside <head>:

<script src="../js/config.js"></script>          <!-- plain script, runs first -->
<script type="module" src="../js/api.js"></script> <!-- module, deferred automatically -->

7 Create Empty __init__.py Files

Python needs __init__.py to treat folders as importable packages. Without these, from agents.orchestrator import run_pipeline fails with a ModuleNotFoundError.

terminal — create empty init files bash 
# Windows (PowerShell):
New-Item agents/__init__.py, routers/__init__.py, utils/__init__.py -ItemType File

# Mac / Linux:
touch agents/__init__.py routers/__init__.py utils/__init__.py

All three files stay empty — just their existence is what matters for Python's import system.
