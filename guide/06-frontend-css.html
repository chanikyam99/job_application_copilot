Section 06

Frontend CSS

The complete design system for the Co-Pilot app. One file, ~500 lines, dark theme throughout.

1. CSS Custom Properties (Design Tokens)

WHY Design Tokens?

CSS custom properties (variables) let you change the entire theme by editing 10 lines. Every color, spacing, radius, and shadow is defined once here and referenced everywhere. If you want a light theme, you override :root in a media query. No find-and-replace across 500 lines.

frontend/css/main.css css

2. Reset & Base Styles

WHY a Reset?

Box-sizing border-box means padding and border are included in width/height — no unexpected overflow. The default browser margin/padding causes cross-browser inconsistencies. Importing Inter from Google Fonts gives a professional clean look consistent with modern SaaS apps.

frontend/css/main.css css

3. Navbar

WHY Sticky Navbar?

Fixed navbar at top with position: sticky; top: 0; z-index: 100 keeps navigation always visible. The glass effect (backdrop-filter: blur) works on modern browsers and gives depth. Logo on left, user actions on right — standard SaaS layout the user recognizes immediately.

frontend/css/main.css css

4. Buttons

WHY Modifier Classes?

A base .btn class + modifier classes (.btn-primary, .btn-secondary, .btn-danger, .btn-sm, .btn-lg) is the standard approach. You never repeat border-radius, padding, font-weight — just compose classes. Transition on all properties gives smooth hover state without specifying each one.

frontend/css/main.css css

5. Form Elements

WHY Custom Form Inputs?

Custom form inputs match the dark theme — browsers default to light inputs which look jarring on a dark background. The focus ring uses box-shadow instead of outline for better cross-browser consistency and rounded corners. Label hints (.label-hint) show validation guidance without cluttering the label.

frontend/css/main.css css

6. Cards

WHY Card Components?

Card components are the atomic UI unit for both the dashboard application grid and the detail page sections. cursor: pointer + translateY(-2px) hover gives subtle interactivity feedback. The company logo placeholder (.app-company-logo) uses a colored circle with the first letter — zero images needed.

frontend/css/main.css css

7. Status Badges

WHY Color-Coded Badges?

Color-coded status badges give instant visual scanning — users can tell application status at a glance without reading text. Each status has its own semantic color. Border + transparent background is softer than solid fills.

frontend/css/main.css css

8. Dashboard Stats

WHY a Stats Row?

The stats row gives an at-a-glance pipeline summary. Large number + small label is a proven metric-display pattern from analytics dashboards. The border-bottom + colored value catches the eye without being distracting.

frontend/css/main.css css

9. File Dropzone

WHY a Dropzone Pattern?

Drag-and-drop requires a large click target and clear visual feedback for "dragging over" state. The dashed border + centered text is the universal pattern for upload zones. The .drag-over class (added by JS on dragenter) highlights the zone so users know it's a valid drop target.

frontend/css/main.css css

10. Step Indicator (New Application Form)

WHY a Step Indicator?

A step indicator shows progress through the 3-step new-application flow. Numbered circles + connecting lines — the standard "wizard" pattern. The active step is highlighted; completed steps show a checkmark. Users know exactly where they are and how many steps remain.

frontend/css/main.css css

11. Tabs (Application Detail)

WHY Tabs for the Detail View?

Tabs are the right pattern for the 4 artifact views (Fit / Resume / Cover Letter / Interview). They keep all results accessible without scrolling past each other. The active tab has a bottom border indicator — a clear, widely understood affordance.

frontend/css/main.css css

12. Score Ring (Fit Analysis)

WHY an SVG Score Ring?

An SVG circle with stroke-dashoffset gives a smooth animated score ring. Setting stroke-dasharray to the circumference (2πr = 276.46 for r=44) lets you set stroke-dashoffset as a percentage to fill the ring. This is pure CSS/SVG — no canvas, no library. Rotate -90° so the ring starts at top.

frontend/css/main.css css

13. Diff View (Resume Rewrite)

WHY a Diff View?

The diff view shows original vs rewritten resume side-by-side. --diff-del red for removed text (with line-through), --diff-add green for added. This is the exact same visual pattern as GitHub diffs — instantly recognizable. The change cards below the diff summarize each specific improvement.

frontend/css/main.css css

14. Interview Accordion

WHY an Accordion for Q&A?

Accordion pattern for interview Q&A — only one question expanded at a time keeps the page from being overwhelming. Click the header to toggle. Type badges (behavioral/technical/situational) give color at a glance. STAR answer structure is shown clearly (Situation, Task, Action, Result).

frontend/css/main.css css

15. Auth Page Layout

WHY Split-Panel Auth?

Split-panel auth layout (hero left + form right) is the design pattern used by Notion, Linear, Vercel, and most modern SaaS tools. The hero panel communicates value; the form is minimal and focused. Centering the form card vertically with align-items: center ensures it looks right on all screen heights.

frontend/css/main.css css

16. Toast Notifications & Loading Overlay

WHY Toasts and an Overlay?

Toast notifications appear in the bottom-right corner and auto-dismiss after 3 seconds — this is the standard non-blocking feedback pattern. The loading overlay covers the entire screen during AI generation (15-30 seconds) so the user knows the app is working and can't accidentally double-submit.
