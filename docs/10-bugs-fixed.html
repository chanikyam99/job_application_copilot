Section 10

Bugs Fixed

6 runtime crashes were silently breaking the app. Every one has been fixed directly in the source files. This page explains what was wrong and what changed so you can verify on the other laptop.

✅ All applied — nothing to re-do

These changes are already in frontend/js/api.js and frontend/application.html. If you copied/cloned this repo, they are already in place. Just read this page to understand what was fixed and why.

1 api.js — getBlob method was missing

File: frontend/js/api.js

Symptom: Clicking "Download .docx" threw TypeError: api.getBlob is not a function. The download button did nothing.

Root cause: application.html called api.getBlob(...) but the api object in api.js only had get, post, patch, delete, postForm. The regular api.get() calls res.json() which fails on binary (.docx) responses — a separate method is needed to return the raw Blob.

What was added at the bottom of the api export object in api.js:

frontend/js/api.js — new method added js 
// ADDED: For binary file downloads (.docx, PDF).
// The regular get() calls res.json() which fails on binary responses.
// getBlob() returns the raw Blob so the caller can create an object URL for download.
getBlob: async (path) => {
  const headers = {};
  const token = auth.getToken();
  if (token) headers['Authorization'] = `Bearer ${token}`;
  const res = await fetch(`${BASE_URL}${path}`, { method: 'GET', headers });
  if (res.status === 401) {
    auth.clear();
    window.location.href = 'index.html';
    return;
  }
  if (!res.ok) {
    const data = await res.json().catch(() => ({}));
    throw new Error(data.detail || `HTTP ${res.status}`);
  }
  return res.blob();
},

2 Status update URL was wrong — always 404

File: frontend/application.html

Symptom: Changing the status dropdown (Not Applied → Applied etc.) appeared to do nothing. The status never saved.

Root cause: The frontend called PATCH /applications/5 but the backend endpoint is at PATCH /applications/5/status. The missing /status suffix caused a 405 Method Not Allowed.

frontend/application.html — status event listener js 
// BEFORE (broken — wrong URL, no /status suffix):
await api.patch(`/applications/${appId}`, { status: e.target.value });

// AFTER (fixed):
// BUG FIX: was /applications/${appId} — backend endpoint is /applications/{id}/status
await api.patch(`/applications/${appId}/status`, { status: e.target.value });

3 Cover letter download URL was wrong — always 404

File: frontend/application.html

Symptom: After fixing Bug 1, clicking "Download .docx" would throw a 404 error.

Root cause: Frontend fetched /applications/5/cover-letter but the backend serves it at /applications/5/download/cover-letter. The /download prefix was missing.

frontend/application.html — download button js 
// BEFORE (broken — wrong URL):
const blob = await api.getBlob(`/applications/${appId}/cover-letter`);

// AFTER (fixed):
// BUG FIX 1: URL was /cover-letter — backend serves at /download/cover-letter
// BUG FIX 2: api.getBlob did not exist — now added to api.js
const blob = await api.getBlob(`/applications/${appId}/download/cover-letter`);

4 Regenerate — URL format wrong (query param vs path param)

File: frontend/application.html

Symptom: All three "↺ Regenerate" buttons (Resume, Cover Letter, Interview) showed a toast but the content never updated — the API returned 422 Unprocessable Entity.

Root cause: Frontend sent POST /applications/5/regenerate?section=resume (query string) but the backend endpoint is POST /applications/5/regenerate/{section} (path parameter). FastAPI didn't find the {section} path segment and returned 422.

frontend/application.html — regenerate function js 
// BEFORE (broken — query param, not path param):
const data = await api.post(`/applications/${appId}/regenerate?section=${section}`, {});

// AFTER (fixed):
// BUG FIX: was ?section=X (query param) — backend expects /{section} (path param)
const data = await api.post(`/applications/${appId}/regenerate/${section}`, {});

5 Regenerate — section names didn't match the backend

File: frontend/application.html

Symptom: Even if the URL were fixed, Resume and Interview regenerate would return HTTP 400 "Invalid section".

Root cause: The frontend event listeners passed 'resume_rewrite' and 'interview_qa' as the section name. The backend's regenerate_section endpoint only accepts: fit_analysis, resume, cover_letter, interview. The longer names were rejected with a 400.

frontend/application.html — regenerate event listeners js 
// BEFORE (broken — wrong section names):
document.getElementById('regen-resume').addEventListener('click',
  () => regenerate('resume_rewrite', renderResume));      // 400: invalid section
document.getElementById('regen-interview').addEventListener('click',
  () => regenerate('interview_qa', renderInterview));     // 400: invalid section

// AFTER (fixed — names must match the backend path param):
// BUG FIX: 'resume_rewrite' → 'resume',  'interview_qa' → 'interview'
document.getElementById('regen-resume').addEventListener('click',
  () => regenerate('resume', renderResume));
document.getElementById('regen-interview').addEventListener('click',
  () => regenerate('interview', renderInterview));

6 Regenerate — response data access was wrong (always undefined)

File: frontend/application.html

Symptom: Even if all previous bugs were fixed, after regenerating, the tab would go blank or show stale content.

Root cause: The regenerate endpoint returns the full ApplicationOut object — the draft is nested at data.draft.resume_rewrite. The old code did renderFn(data[section]) which would be data['resume_rewrite'] → undefined (that field doesn't exist at the top level). Additionally, the draft field names differ from the backend section names (e.g. path param 'resume' → field draft.resume_rewrite), so a mapping table is needed.

frontend/application.html — full fixed regenerate function js 
// Maps the backend path-param section name → Draft model field name.
// The backend uses short names in the URL; the DB field names differ.
const SECTION_FIELD = {
  fit_analysis: 'fit_analysis',   // stores JSON
  resume:       'resume_rewrite', // stores JSON {text, changes}
  cover_letter: 'cover_letter',   // stores plain text
  interview:    'interview_qa',   // stores JSON array
};

async function regenerate(section, renderFn) {
  try {
    toast('Regenerating...', 'info');
    // FIX 1: path param not query param
    // FIX 2: data.draft[field] not data[section]
    // FIX 3: section names match backend values
    const data  = await api.post(`/applications/${appId}/regenerate/${section}`, {});
    const field = SECTION_FIELD[section];
    let value   = data.draft ? data.draft[field] : null;
    // Parse JSON strings — same logic as renderAllTabs()
    if ((field === 'fit_analysis' || field === 'resume_rewrite' || field === 'interview_qa')
        && typeof value === 'string') {
      value = JSON.parse(value);
    }
    if (value) renderFn(value);
    toast('Regenerated!', 'success');
  } catch (err) { toast(err.message, 'error'); }
}
Why so many bugs in one place?

The regenerate feature was likely written before the backend endpoint was finalized. The URL format, section naming, and response shape all diverged between the frontend and backend and were never reconciled. These are integration bugs — each file worked in isolation but didn't agree on the contract.
