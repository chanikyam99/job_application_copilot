2 Flow 1 — Sign Up / Login

1
User fills email + password on index.html
JS calls api.post('/auth/login', {email, password}) — no auth header needed here.
2
FastAPI verifies password with bcrypt, creates a JWT token
jwt.encode({"sub": email, "exp": now + 7 days}, SECRET_KEY) — signed, not encrypted. Never stores sessions.
3
JS stores the token: localStorage.setItem('token', ...)
Persists across page loads. From now on, every api.* call automatically adds Authorization: Bearer <token>.
✓
Redirected to dashboard.html
Any 401 response from any endpoint auto-clears localStorage and redirects back to login.

3 Flow 2 — Create an Application

1
Step 1 — User drops a PDF onto the upload zone
File is held in browser memory. Nothing uploaded yet.
2
Step 2 — User fills job title, company, pastes the full JD
More detailed JD = better agent output. Copy directly from a LinkedIn job post.
3
Click "Generate My Kit" — JS builds a FormData + posts to POST /applications/
FastAPI receives the PDF binary, runs it through pypdf, saves the extracted text as original_resume. The raw PDF is not stored.
4
Immediately calls POST /applications/{id}/generate — loading screen shows
The AI pipeline runs (~15–30s). Step 3 of the wizard shows animated progress.
✓
Redirected to application.html?id={id}
All 4 tabs are populated with AI output from the database.

4 Flow 3 — The AI Generation Pipeline

This is the core of the app. One API call triggers 4 LLM agents. Agent 1 runs first; Agents 2, 3, 4 run simultaneously with asyncio.gather().

1
Agent 1 — Fit Analyst (sequential, ~5s)
Compares resume vs JD. Returns {match_score, matching_requirements, missing_requirements, skills_to_emphasize, key_keywords}. Its output feeds Agents 2, 3, 4.
2
Agents 2 + 3 + 4 launch in parallel via asyncio.gather() (~10s)
Agent 2 · Resume Writer
Rewrites bullets with JD keywords. Returns {rewritten_resume, changes:[{original, rewritten, reason}]}
Agent 3 · Cover Letter
1-page letter tone-matched to the company. Returns plain text.
Agent 4 · Interviewer
10 Q&As. Returns [{type, question, sample_answer, tip}]
3
All results saved to the drafts table as JSON strings
json.dumps(result) before INSERT. Parsed back to objects with json.loads() when the frontend fetches them.
✓
Total: ~15s  ·  Sequential would be ~45s  ·  3× faster from parallelism

5 Flow 4 — Viewing & Using Results

1
application.html reads ?id=X from the URL, calls GET /applications/X
One API call returns the full application with the embedded draft object.
2
Fit Analysis tab — score ring, matching/missing tags, skills + keyword chips
JSON.parse(draft.fit_analysis) → reads match_score → animates SVG ring via stroke-dashoffset.
3
Resume tab — original left, rewritten right, change cards below
JSON.parse(draft.resume_rewrite) → renders the diff view and each change with its reason.
4
Cover Letter tab — readable letter + Download .docx button
GET /applications/{id}/download/cover-letter → backend generates .docx with python-docx → browser downloads via Content-Disposition: attachment.
5
Interview Prep tab — 10 expandable Q&As with type badges
JSON.parse(draft.interview_qa) → accordion cards, each with type (behavioral/technical/situational), question, sample answer, coaching tip.
6
Status dropdown + ↺ Regenerate buttons
Status: PATCH /applications/{id}/status. Regenerate: POST /applications/{id}/regenerate/{section} — re-runs one agent only, ~10s, without touching the other tabs.

Why store agent output as JSON text?

Each agent returns a different structure (score + arrays vs plain text vs Q&A list). Rather than creating 4 separate tables with different columns, each output is json.dumps()-ed before INSERT and json.loads()-ed after SELECT. This keeps the schema simple — the structure is defined by the agent prompt, not the database.
